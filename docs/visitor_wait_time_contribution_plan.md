# GitHub Pages + Firebaseによる来校者混雑報告案

クラス企画が忙しく、各企画担当が待ち時間を入力する運用は難しいという前提で考えます。  
また、来校者は学校のWi-Fiを使えず、校内LAN上の白龍AIガイド本体へ直接アクセスできません。来校者が使えるのは、自分のスマホ回線から開ける外部公開ページです。

そのため、来校者向けの入力は **GitHub Pages** に置き、入力内容は **Firebase** に保存し、本番PC側の白龍AIガイドが1分に1回ほどFirebaseから情報を取得する構成が現実的です。

## 1. 結論

この案はかなり有効です。  
来校者スマホが学校ネットワークに入れなくても、GitHub PagesとFirebaseなら外部回線からアクセスできます。

構成:

```text
来校者スマホ
  ↓ 外部回線
GitHub Pagesの混雑報告ページ
  ↓
Firebase Realtime Databaseに保存
  ↓ 1分に1回
本番PC側の白龍AIガイドがFirebaseから取得
  ↓
設置タブレット・PCの画面に混雑目安として表示
```

ここで大事なのは、来校者入力を「正確な待ち時間」として扱わないことです。  
表示は **待ち時間** ではなく **来校者報告による混雑目安** にします。

## 2. 何を入力してもらうか

来校者には分数を入力してもらわず、4択ボタンにします。

```text
この企画はいまどれくらい混んでいますか？

[すぐ入れそう]
[少し待つ]
[かなり混んでいる]
[受付停止・満員っぽい]
```

理由:

- 来校者が正確な待ち時間を測るのは難しい。
- 分数入力は面倒で、入力ミスが起きやすい。
- 4択ならスマホで押しやすい。
- 集計して「混雑の傾向」として扱いやすい。

## 3. 画面の置き場所

### 来校者入力ページ

GitHub Pagesに置きます。

例:

```text
https://kali-n-coder.github.io/bunka-AI/crowd/
```

または待ち時間ページと統合する場合:

```text
https://kali-n-coder.github.io/bunka-AI/wait/
```

来校者は、掲示されたQRコードからこのページを開きます。

### 白龍AIガイド本体

本番PC上で動かします。  
来校者スマホから直接アクセスさせません。

設置タブレットやPCは、校内で本番PCにアクセスできる端末として使います。

## 4. QRコードの考え方

### 案A: 全体QRを1つだけ掲示する

1つのQRから混雑報告ページを開き、来校者が企画を選んで報告します。

メリット:

- 掲示が楽。
- QRコードを1種類だけ作ればよい。
- 受付、ポスター、パンフ補助掲示に置きやすい。

デメリット:

- 企画選択ミスが起きる可能性がある。
- 企画一覧から探す手間がある。

### 案B: 企画ごとのQRを作る

各企画の前に、その企画専用のQRを貼ります。

例:

```text
https://kali-n-coder.github.io/bunka-AI/crowd/?id=32
```

メリット:

- 企画選択ミスが少ない。
- その企画の前にいる人が入力しやすい。

デメリット:

- QRを企画ごとに作る必要がある。
- 貼り間違いが起きる可能性がある。
- 全企画分の掲示管理が大変。

### おすすめ

最初は **全体QRを1つ** でよいです。  
余裕があれば、混みやすい飲食・体験企画だけ企画別QRを作るのが現実的です。

## 5. Firebaseに保存するデータ

Firebase Realtime Databaseを使う想定です。

保存形式の案:

```json
{
  "crowdReports": {
    "32": {
      "-autoId1": {
        "exhibitionId": 32,
        "status": "busy",
        "createdAt": 1710000000000
      },
      "-autoId2": {
        "exhibitionId": 32,
        "status": "short",
        "createdAt": 1710000030000
      }
    }
  }
}
```

`status` の候補:

| 値 | 表示 | 意味 |
| :--- | :--- | :--- |
| `empty` | すぐ入れそう | ほぼ並んでいない |
| `short` | 少し待つ | 少し列がある |
| `busy` | かなり混んでいる | 明確に列がある |
| `closed` | 受付停止・満員っぽい | 入れない、またはかなり厳しそう |

最初はこれだけで十分です。

保存しないもの:

- 名前
- 学年
- クラス
- 電話番号
- メールアドレス
- 位置情報
- 自由記述コメント

自由記述は入れない方が安全です。悪ふざけや個人情報が入る可能性があるためです。

## 6. 本番PC側の取得方法

本番PC側の白龍AIガイドが、Firebaseから定期的に報告を取得します。

おすすめ:

- 1分に1回取得する。
- 取得対象は直近15分程度の報告だけにする。
- 取得結果をローカルDBまたはメモリに反映する。
- 設置タブレット・PCの表示には、その集計結果を出す。

リアルタイム同期にこだわる必要はありません。  
文化祭の混雑目安なら、1分遅れでも十分実用的です。

## 7. 集計方法

正確な待ち時間ではなく、直近報告から混雑目安を作ります。

### 7.1 直近の報告だけ使う

古い報告は使いません。

おすすめ:

- 直近15分以内の報告を使う。
- 15分を超えたら「情報が古い」と表示する。
- 30分以上報告がなければ「情報なし」に戻す。

### 7.2 表示は状態で出す

避けたい表示:

```text
待ち時間: 10分
```

おすすめ表示:

```text
来校者報告: かなり混んでいる
最近の報告: 8件
最終報告: 3分前
```

報告が少ない場合:

```text
来校者報告: 参考情報
最近の報告: 1件
最終報告: 12分前
```

報告が古い場合:

```text
来校者報告: 情報が古いです
最終報告: 32分前
```

### 7.3 分数に変換する場合

分数に変換する場合も、必ず「目安」と書きます。

| 報告 | 表示する目安 |
| :--- | :--- |
| すぐ入れそう | 0〜5分目安 |
| 少し待つ | 10〜15分目安 |
| かなり混んでいる | 20〜40分目安 |
| 受付停止・満員っぽい | 受付停止・満員の可能性 |

ただし、最初は分数変換しない方が安全です。

## 8. Firebaseルールの考え方

連投防止や信頼度の細かい実装は後回しでよいです。  
ただし、最低限の安全として、Firebase側で保存できる形だけは制限したいです。

最低限やりたいこと:

- `status` は `empty`, `short`, `busy`, `closed` のどれかだけ。
- `exhibitionId` は数値だけ。
- `createdAt` は数値だけ。
- 自由記述欄を保存しない。
- 読み取り・書き込みできるパスを `crowdReports` に限定する。

イメージ:

```text
crowdReports には決まった形のデータだけ書ける。
それ以外の場所には書けない。
```

細かい認証や連投対策は、本番PCがひと段落してからでよいです。

## 9. 表示の文言

来校者報告は断定しない文言にします。

### 入力ページ

```text
近くで見た範囲で、いまの混み具合を教えてください。
正確でなくても大丈夫です。みんなの案内の参考になります。
```

### 送信後

```text
ありがとうございます。
あなたの報告は、混雑目安として反映されます。
```

### 待ち時間一覧

```text
混雑目安は来校者からの匿名報告をもとにしています。
実際の待ち時間や受付状況は、現地の案内を確認してください。
```

## 10. 本番PC側の表示案

待ち時間一覧に、スタッフ入力と来校者報告を分けて表示します。

```text
オカダナルド
スタッフ更新: なし
来校者報告: かなり混んでいる
最近の報告: 8件
最終報告: 3分前
```

スタッフ入力がある場合:

```text
オカダナルド
スタッフ更新: 20分
来校者報告: かなり混んでいる
最近の報告: 8件
最終報告: 3分前
```

スタッフ更新と来校者報告が食い違う場合も、どちらかを消さずに並べた方が安全です。

```text
スタッフ更新: 5分
来校者報告: かなり混んでいる
```

この場合は「現地案内を確認してください」と出します。

## 11. admin画面にあると便利なもの

実装は後回しでよいですが、将来的にはadmin画面に次を出すと便利です。

```text
企画名 | 来校者報告 | 報告数 | 最終報告
```

管理者が見る目的:

- どの企画が混んでいそうか把握する。
- スタッフ更新ができない企画の代替情報にする。
- 明らかに変な報告が続いていないか見る。

## 12. 実装タスク案

本番PCがひと段落してから、次の順に実装するのがよいです。

### フェーズ1: GitHub Pages側

1. `frontend/public/crowd/` のような専用ページを作る。
2. 企画一覧を表示する。
3. 企画を選ぶと4択ボタンを表示する。
4. 選択内容をFirebase Realtime Databaseへ保存する。
5. 送信完了メッセージを出す。

### フェーズ2: Firebase

1. `crowdReports` 用のデータ構造を作る。
2. 書き込みルールを最低限設定する。
3. 自由記述なし、4択だけにする。
4. GitHub Pagesから書き込めることを確認する。

### フェーズ3: 本番PC側

1. Firebaseから1分に1回データを取得する処理を作る。
2. 直近15分の報告だけ集計する。
3. 企画ごとに混雑目安、報告数、最終報告時刻を作る。
4. 待ち時間一覧に表示する。
5. admin画面にも表示する。

### フェーズ4: AI連携

余裕があれば、AIにも来校者報告を見せます。

例:

```text
今混んでいる企画は？
```

回答例:

```text
来校者報告では、オカダナルドがかなり混んでいるようです。
ただし目安なので、現地の案内も確認してください。
```

## 14. この案の良いところ

- 来校者が学校Wi-Fiに入れなくても使える。
- 本番PCを外部公開しなくてよい。
- 来校者スマホからFirebaseへ直接保存できる。
- 本番PC側は1分に1回取りに行くだけでよい。
- スタッフ入力が無理な企画でも、混雑の傾向を出せる。
- 既存のGitHub Pages待ち時間ページと相性がよい。

## 15. 注意点

- 来校者報告は正確な待ち時間ではありません。
- 表示は必ず「目安」にします。
- 自由記述は入れません。
- 個人情報は集めません。
- 本番PCがFirebaseにアクセスできるネットワーク環境が必要です。
- Firebase設定やGitHub Pages設定は、本番PCがひと段落してから行います。

# 白龍AIガイド これからやることリスト

このドキュメントは、現在の本番用データと実装状況を前提に、これから本番運用までにやるべきことをまとめたものです。  
開発だけでなく、生徒会確認、未確定情報の扱い、タブレット・PC設置、当日の運用体制まで含めています。

## 0. 現状

- 本番用企画データは `docs/data/production/exhibitions.csv` に53件あります。
- AI用データは `docs/data/production/knowledge.json` と `docs/data/production/knowledge.md` にあります。
- 画像PDFのパンフから読める内容はかなり反映済みです。
- 料金、正式名称、アレルギー、ステージ予定の一部は確認済みです。
- 残っている不明点は、これ以上は分からないものとして本番データに登録済みです。AIには推測で補完させない方針です。
- このPCは本番用ではないため、本番DB投入、RAG本番投入、PIN再生成、Firebase本番設定は本番PCで行います。

## 1. 最優先で生徒会・実行委員に確認すること

### 1.1 AIガイドを置いてよい場所

生徒会または実行委員に、来場者向け端末をどこに置けるか確認してください。

確認したいこと:

- 受付付近に置けるか。
- 生徒会室付近に置けるか。
- 校内案内・迷子・落とし物対応の近くに置けるか。
- 電源を使ってよい場所か。
- Wi-Fiまたは有線LANが使える場所か。
- 来場者が立ち止まっても通行の邪魔にならない場所か。
- 雨天時や混雑時でも運用できる場所か。
- 先生やスタッフが近くで見守れる場所か。

おすすめ候補:

| 候補 | よい点 | 注意点 |
| :--- | :--- | :--- |
| 正門入口・受付付近 | 来場直後に使える。パンフ代わりの案内に向く。 | 混雑しやすい。端末前に人がたまる可能性がある。 |
| 1F生徒会室付近 | 迷子・落とし物案内と相性がよい。スタッフが近い。 | 入口から遠い場合、初見の来場者が気づきにくい。 |
| 体育館・ステージ付近 | ステージ予定確認に向く。 | ステージ待機列や音で使いにくい可能性がある。 |
| 中央階段・主要導線付近 | 多くの人の目に入る。 | 通行の邪魔になりやすい。設置許可と安全確認が必要。 |
| 飲食エリア付近 | 待ち時間やラストオーダー案内に向く。 | 飲食物が端末にこぼれるリスクがある。 |

最初のおすすめは、`受付付近に1台`、`生徒会室付近に1台` です。  
1台しか置けないなら、受付付近がもっとも効果が出やすいです。

### 1.2 来場者が使う端末の種類

確認すること:

- タブレットを使うのか、ノートPCを使うのか、デスクトップPCを使うのか。
- 何台用意できるか。
- 画面サイズはどのくらいか。
- タッチ操作できるか。
- キーボード入力を許可するか。
- 盗難防止、破損防止、落下防止をどうするか。
- 常時電源につなげるか。
- スリープしない設定にできるか。

運用としては、来場者用はタブレットまたはタッチ対応PCが理想です。  
キーボード入力が必要なチャットは便利ですが、誤入力やいたずらも起きるので、設置場所にスタッフがいる方が安全です。

### 1.3 AIチャットを来場者に公開してよいか

AIチャットは便利ですが、文化祭当日の公開には確認が必要です。

確認すること:

- 来場者が自由入力で質問してよいか。
- 不適切な入力があった場合の対応をどうするか。
- AIが間違えた場合、誰が修正・説明するか。
- 「AIの回答は参考情報です。最終案内はスタッフに確認してください」のような注意文が必要か。
- 個人情報、写真、SNS投稿、緊急時案内などの質問にどう答えさせるか。

安全寄りにするなら、当初は以下の運用がおすすめです。

- 来場者端末では `待ち時間`、`企画一覧`、`ステージ予定` を中心に使う。
- AIチャットはスタッフが近くにいる端末だけで使う。
- AI回答には「資料にないことは分かりません」と言わせる。

## 3. データ面でやること

### 3.1 追加情報をCSVに反映

追加情報が入ってきたら、まず `docs/data/production/exhibitions.csv` を更新します。現時点で分からない項目は、無理に埋めず「現時点の資料では確認できません」として残します。

特に直す列:

- `description`: 来場者が何をする企画か分かる説明にする。
- `duration_minutes`: 所要時間を仮値から実値へ近づける。
- `recommended_for`: どんな人におすすめかを書く。
- `cautions`: 料金、人数制限、撮影、怖さ、整理券、売り切れなどを書く。
- `ticket_status`: 有料/無料ではなく、必要なら `整理券あり`、`予約あり`、`食券あり` などに直す。
- `capacity_status`: 満員に近い、残りわずかなど当日運用するか決める。

### 3.2 AI用データを再生成・再投入

CSVを直したら、`knowledge.json` も更新します。  
現在はCSVから再生成しているため、CSVとAI用JSONがズレないようにしてください。

本番PCで更新後に実行するコマンド:

```powershell
backend\venv\Scripts\python.exe backend\scripts\validate_exhibition_data.py --profile production
backend\venv\Scripts\python.exe backend\scripts\seed_exhibitions_from_data.py --profile production
backend\venv\Scripts\python.exe backend\scripts\ingest_documents.py --profile production
```

### 3.3 スタッフPINを作り直す

企画数が増減した場合、スタッフPINを作り直します。これは本番PCで行います。このPCでは勝手に作り直しません。

```powershell
backend\venv\Scripts\python.exe backend\scripts\generate_staff_pins.py
```

作り直したら、各企画担当に以下を渡します。

- 企画ID
- 企画名
- PIN
- 待ち時間更新画面のURL
- 更新ルール

### 3.4 このPCでやらないこと

このPCは本番用ではないため、ここでは本番環境を変える作業を行いません。  
このPCでやってよいのは、データ編集、ドキュメント更新、検証、画面確認までです。

このPCではやらないこと:

- 本番DBへの投入。
- 本番RAGデータの投入。
- スタッフPINの本番用再生成。
- admin PINの本番設定。
- Firebase Realtime Databaseの本番設定変更。
- 当日使う端末としての運用。

## 4. タブレット・PC設置で決めること

### 4.1 設置台数

最低ライン:

- 来場者用端末 1台
- 管理・スタッフ確認用PC 1台

できれば:

- 受付付近に来場者用 1台
- 生徒会室付近に来場者用 1台
- 管理者用PC 1台
- スマホ向け待ち時間ページをQRで掲示

### 4.2 設置場所ごとの役割

| 場所 | 端末の役割 |
| :--- | :--- |
| 受付付近 | 初めて来た人向け。企画一覧、現在の待ち時間、ステージ予定を見せる。 |
| 生徒会室付近 | 困った人向け。迷子、落とし物、場所案内、スタッフ確認に使う。 |
| 飲食エリア付近 | 飲食企画、ラストオーダー、アレルギー、混雑状況を見せる。 |
| ステージ付近 | ステージ予定、雨天時変更、次の演目を見せる。 |

### 4.3 物理的な安全

考えること:

- 端末を机に固定するか。
- 充電ケーブルを養生テープなどで固定するか。
- ケーブルで来場者がつまずかないか。
- 飲食物が近くに置かれないか。
- 画面を明るくしすぎてバッテリーが減らないか。
- スリープしない設定にするか。
- 誰が端末を見回るか。
- 雨天時、屋外近くに置かないか。

### 4.4 画面表示の運用

来場者用端末は、最初に開く画面を決めてください。

おすすめ:

- 受付付近: `企画一覧` または `待ち時間`
- 生徒会室付近: `白龍に相談`
- 飲食エリア: `待ち時間`
- ステージ付近: `企画一覧` かステージ予定を案内できる画面

来場者が迷いやすい場合は、端末の横に紙で短く書いておくとよいです。

```text
白龍AIガイド
企画・場所・待ち時間を調べられます。
困ったら近くのスタッフに声をかけてください。
```

## 5. 待ち時間運用で決めること

### 5.1 どの企画が待ち時間更新の対象か

全53件を更新する必要はありません。  
待ち時間更新の対象は、来場者が並びやすい企画だけに絞る方が現実的です。

優先対象:

- ホラー・脱出・迷路系
- ゲーム系
- 飲食系
- 体験型で人数制限があるもの
- ステージではなく、教室や屋外で列ができるもの

更新しなくてもよい可能性が高いもの:

- 展示
- 休憩室
- 写真展示
- 書道展
- 一般公開終了、ラストオーダーなどの案内項目

### 5.2 更新頻度

おすすめルール:

- 空いているとき: 15〜30分ごと
- 混んできたとき: 5〜10分ごと
- 大きく変わったとき: すぐ更新
- 昼前後・ステージ直後: こまめに更新

### 5.3 待ち時間の入力基準

スタッフごとに感覚が違うと表示がぶれます。  
次の基準を共有するとよいです。

| 状態 | 入力目安 |
| :--- | :--- |
| すぐ入れる | 0〜5分 |
| 少し待つ | 10分 |
| 明確に列がある | 20分 |
| かなり混んでいる | 30〜45分 |
| 受付停止に近い | 60分以上、または満員表示を検討 |

### 5.4 スマホ向け待ち時間ページ

スマホから待ち時間だけ見られるページはGitHub Pages用に分離済みです。

確認すること:

- GitHub PagesのURLをQRコード化する。
- 受付、パンフ、掲示物にQRコードを置くか決める。
- Firebase Realtime Databaseを本番用に設定する。
- ローカルの待ち時間更新がFirebaseへ反映されるか確認する。
- 当日、スマホで外部ネットワークから開けるか確認する。

## 6. 生徒会・先生に確認すること

### 6.1 情報公開の確認

確認すること:

- 企画情報をAIガイドに入れて公開してよいか。
- GitHub Pagesの待ち時間ページを外部公開してよいか。
- QRコードを校内に掲示してよいか。
- 待ち時間をスマホで見せてよいか。
- ステージ予定の変更情報をどう反映するか。

### 6.2 個人情報・写真・SNS

パンフには写真、動画の二次利用やアップロードに関する注意があります。  
AIが案内するときも、この方針と矛盾しないようにする必要があります。

確認すること:

- 写真撮影が禁止または制限される企画はあるか。
- SNS投稿してよい範囲はどこまでか。
- AIに「写真を撮れる企画」を聞かれたとき、どう答えるべきか。
- 生徒名や個人情報に関する質問には答えない方針でよいか。

### 6.3 緊急時案内

AIに緊急時の判断をさせるのは危険です。  
緊急時は必ずスタッフ・先生の指示へ誘導する運用にしてください。

決めること:

- 地震、火災、体調不良、迷子、落とし物への定型回答。
- 体調不良は1階保健室へ案内する。
- 迷子・落とし物は1階生徒会室へ案内する。
- 災害時は本校職員・白龍祭スタッフの指示に従う。

## 8. 当日の運用体制

### 8.1 役割分担

最低限、次の役割を決めてください。

| 役割 | やること |
| :--- | :--- |
| 管理者 | PC起動、admin画面、Firebase反映、トラブル対応 |
| 待ち時間更新担当 | 各企画から待ち時間を集める、または企画担当へ更新を依頼 |
| 端末見回り担当 | 来場者端末の画面、電源、通信、いたずらを確認 |
| 情報確認担当 | ステージ変更、売り切れ、雨天対応を確認して反映 |
| 先生・生徒会連絡係 | 判断が必要な情報を先生や生徒会に確認 |

### 8.2 トラブル時の対応

想定トラブル:

- AIが間違った案内をした。
- ネットが切れた。
- Ollamaが落ちた。
- 待ち時間が更新されない。
- GitHub Pagesに反映されない。
- 来場者が変な質問をした。
- 端末が固まった。

対応方針:

- AIが怪しいときは「スタッフに確認してください」と案内する。
- 端末が固まったらブラウザ更新、それでもだめなら再起動。
- 待ち時間が更新されないときはadmin画面で直接更新。
- GitHub Pagesだけ反映されない場合でも、校内PCの表示を優先する。
- 緊急時はAIではなく先生・スタッフの指示を優先する。
